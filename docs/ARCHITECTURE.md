## 1. システム全景

```
[スマートメーター]
   │ Wi-SUN Bルート（ECHONET Lite / UDP）
   ▼
[BP35A1モジュール] ←UART(115200)→ [親機 M5StickC Plus (UIFlow MicroPython)]
                                      │ smm3_main.py / smm3_main_web.py
                        ┌─────────────┼──────────────┐
                        │ ESP-NOW      │ HTTPS POST    │ HTTPS
                        │ (broadcast)  │ (JSON)        │ (Ambient・任意)
                        ▼              ▼               ▼
                  [子機たち]      [GASダッシュボード]   [Ambient]
                  ・ATOM S3       gas_dashboard/
                    (CircuitPython) Code.js + History.js + Dashboard.html
                  ・Core2 / Basic     │
                    (UIFlow)          ▼
                                 [Google Sheets "SMM3 History"]
```

- **親機がすべてのデータの源泉**。スマートメーターと通信できるのは親機だけで、
  子機・GASは親機からの一方向配信を受けるだけ（子機→親機は履歴リクエストのみ）。
- `smm3_main.py` が従来の親機、`smm3_main_web.py` がGAS送信を加えた現行の親機。
  Web版はフリーズ対策（WDT・タイムアウト・自己復旧）を多数持つ（§5）。

## 2. スマートメーター通信（BP35A1 / ECHONET Lite）

`bp35a1.py` はUART経由でBP35A1にSKコマンドを送るドライバ。

### 接続シーケンス（`BP35A1.open()`）

1. `SKRESET` → エコーバックASCII化（`WOPT 01`）→ `SKTERM`（前セッション解除）
2. BルートID/パスワード設定（`SKSETRBID` / `SKSETPWD`）
3. **アクティブスキャン**（`SKSCAN 2 FFFFFFFF <duration>`、duration=4から失敗ごとに+1、最大7）
   - 結果（Channel / Pan ID / Addr / LQI）は `/flash/smm_scan.json` にキャッシュし、
     次回起動ではスキャンを省略する（スキャンは数十秒かかるため）。
   - `SKJOIN` 失敗時はキャッシュを破棄して再スキャン（メーター交換・チャンネル変更に自動追従）。
4. `SKLL64`（MACアドレス→IPv6リンクローカル変換）→ チャンネル・PAN ID設定 → `SKJOIN`（PANA認証）
5. 係数 `D3` と積算電力量単位 `E1` を取得。**実測値 = 生値 × coefficient × unit**。
   親機は `UNIT = unit * coefficient` として保持する（子機は現状 `UNIT=0.1` 固定。§7参照）。

### 使用しているECHONET Liteプロパティ（DEOJ = 028801 低圧スマート電力量メータ）

| EPC | 内容 | 用途 |
|-----|------|------|
| D3 | 係数 | 初回接続時のみ取得しキャッシュ |
| E1 | 積算電力量単位 | 同上 |
| E2 | 積算電力量履歴（48点/日） | 履歴取得。**E5で対象日を先に書き込む**2段階操作 |
| E5 | 履歴収集日（n日前） | E2の対象日指定（write） |
| E7+E8 | 瞬時電力+瞬時電流 | **OPC=2で1電文にまとめて取得**（往復を半減） |
| EA | 定時積算電力量（30分毎確定値） | 累積値の基準。タイムスタンプ付き |

- E2の応答で `0x05f5e0ff`（=99999999）は「データ無し」のセンチネル → 0に置換。
- E8の電流は R相・T相 各2バイトで、`0x7ffe` は「未計測」→ 0扱い。合算して0.1A単位。
- 読み出しはすべて `wait_for_data()` の1本のパーサーに集約されており、`ERXUDP` 行から
  SEOJ/ESV/EPCを見て振り分ける。**タイムアウトは例外で表現**され、呼び出し側の
  リトライループ（3〜5回）が拾う。リトライを使い切ると上位へ例外が飛び、
  親機は `finally: reset()` で再起動する（§5の例外設計）。

## 3. ESP-NOWワイヤプロトコル

全メッセージ**ブロードキャスト・ACK無し**。文字列ベース（履歴応答のみ一部バイナリ）。
UIFlow側とCircuitPython側でespnow APIは全く違うが（CLAUDE.md「Two Runtimes」）、
電文が共通なので相互運用できる。

### 親機 → 子機

| 電文 | 形式 | タイミング |
|------|------|-----------|
| `M:BOOT` | 固定文字列 | 親機起動時・履歴再取得開始時 |
| `M:INST<watt>/<amp>` | 例 `M:INST1234/12.3` | 10秒毎 |
| `M:CUML<collect>/<created>/<e_energy>/<monthly_kwh>/<charge>` | `/`区切り5フィールド | 10分毎（毎時 x1/x11/x21/x31/x41/x51 分） |
| `M:TOUT` | 固定文字列 | メーターからのデータがTIMEOUT_MAIN秒途絶 |
| `M:UNT=<unit>` | 現在は無効化 | （UNITを子機に配る計画の名残。§7） |
| `M:ID<nn><created:19><date:5><bin:196+1>` | ヘッダはASCII、履歴49点は**ビッグエンディアンuint32×49のバイナリ**＋終端0x00 | REQ応答 |

- `M:ID` 電文は約227バイトで、**ESP-NOWのペイロード上限250バイトに対する余裕は約23バイトしかない**。
  created(19文字)・date(5文字固定幅)・49点という構成を変えるときは上限を必ず意識すること。
- 子機側のパースは後方オフセット基準（`body[-202:-197]`=日付、`body[-197:-1]`=バイナリ）。
  前方に何か足しても壊れないが、後方の構造は変えられない。

### 子機 → 親機

| 電文 | 意味 |
|------|------|
| `REQ00`〜`REQ30` | n日前の履歴データ要求。子機は起動時に**逐次**（応答を待って次へ、30秒で再送）00→30と要求する |

- `REQ00` を受けた親機はCUMLタイマーもリセットする（起動直後の子機にすぐCUMLが届くように）。
- 親機は同一IDへの30秒以内の重複応答をスキップ（複数子機が同時起動したときの応答の嵐を防ぐ）。

## 4. データモデル：49スロットの累積値

親機・子機とも、1日分の履歴を **「00:00〜24:00の30分刻み49スロット × 累積メーター生値」** で持つ。

- `hist_data[d][k]`（親機）/ `hist_week[d][k]`（子機）: d日前・スロットk の累積値（生値、int）。
- **各時間帯の使用量は保存せず、表示時に隣接スロットの差分で計算する**：
  `kwh = (slot[n+1] - slot[n]) * UNIT`
- **0 は「データ無し」のセンチネル**。差分計算は両端が非0のときだけ行う。
  - Why: 累積値なら順序を問わず埋められ、欠けても他のスロットに影響しない。
    ただし1スロット欠けるとその両隣2区間の表示が欠ける（フリーズ調査で問題になった点）。
- スロット49個（48ではなく）なのは **24:00 = 翌日00:00 を両日に持たせる**ため。
  `hist_data[d+1][48] = hist_data[d][0]` で連結する。

### 日跨ぎ処理（親機・子機で同じアルゴリズム）

EAの確定値タイムスタンプで駆動する：

1. `created_time == 00:00` → その値は**当日スロット48**（前日24:00ではなく「今日の終端」扱い）。
2. `created_time == 00:30` かつ `slot[2] != 0`（=まだ昨日のデータが today に残っている）
   → 配列を1日分シフトし、`新today[0] = 昨日[48]` で連結、今日をゼロクリア。
   - Why: 00:00ちょうどのシフトはメーター側の日跨ぎ処理のタイムラグと衝突する。
     00:30の最初のデータ到着を「新しい日が確実に始まった」合図として使う。
   - 親機はこのタイミングでNTP時計合わせも行う（1日1回）。
3. 履歴取得中に `00:00` を踏んだ場合は `day_shift=1` を立てて30秒待つ
   （メーター側の日付繰り上がり遅延の吸収）。

### 料金計算

- `hist_data` から1時間毎の使用量リスト`hourly_power`を作り、`calc_charge.py` の
  `CalcCharge` の**設定で指定されたメソッド**（`getattr(instance, config['CHARGE_FUNC'])`）に渡す。
  電力会社別ロジックの差し替え方法は CLAUDE.md「Modular Charge Calculation」参照。
- 「今月」は検針日起点。`bp35a1.days_after_collect()` が config の検針日カレンダー
  （月別に日が違う）から経過日数を計算する。

## 5. 親機の耐障害設計（smm3_main_web.py）

**歴史的経緯**: GAS送信を追加するまで親機は「何かあれば `finally: reset()` で再起動」だけで
安定していた（フリーズほぼゼロ）。GAS追加後、数日に1回のフリーズが発生し、
以下の多層防御が積まれた。詳細な調査ログは [session-insights.md](session-insights.md)。

### 例外設計の基本形

```
try:  メインループ（各send_xxxは内部try/exceptで握りつぶし、retriesを加算）
except: pass
finally: reset()   ← どんな未捕捉例外でも「再起動」に落とす
```

- 想定される故障モードは「再起動」であって「フリーズ」ではない。
  **フリーズが起きたらこの防御の外側（例外もreturnも出ない無限ブロック）を疑う。**
- `retries >= max_retries(30)` でループを抜けて再起動する軟性ウォッチドッグもあるが、
  Ambient送信成功などでもリセットされるため、単独では当てにならない。

### フリーズへの多層防御（外側から順に）

1. **ハードWDT（120秒）** — urequestsがGAS無応答で無限ブロックしても強制リセット。
   - **履歴取得完了後（定常運転入り）に初めて生成する**。起動時の履歴取得は正当に
     120秒を超えることがあり、起動時から張るとWDT発火→再起動→また履歴取得…の
     ブートループになるため。フリーズは定常運転中にしか起きていないので、そこだけ守る。
   - 120秒 = BP35A1の最大待ち(60s) + sleep(30) を上回る値（誤発火防止）。
   - feedはループ先頭と `check_timeout()`（各ステージ境界で呼ばれる）の2系統。
2. **`_web_post()` = GAS POSTの単一チョークポイント** — 必ず `timeout=` を付ける。
   ただし実機FW 1.12のurequestsは `timeout=` 非対応（TypeError）なので、初回失敗で
   フラグを落として以後は付けず、**ハングはWDTに委ねる**。
3. **GASの302リダイレクトは成功扱い** — GASは `doPost` 実行後302を返し、urequestsが
   "Redirects not yet supported" 例外を出すが**処理自体は成功している**（実機検証済み）。
   `'Redirect' in str(e)` で成功に読み替える。この読み替えを消すと全送信が失敗扱いになる。
4. **WiFi起動時自動リトライ** — `autoConnect(lcdShow=True)` は失敗時にUIFlowの
   オレンジ画面でボタン待ち＝無人運用では永久停止するため、`lcdShow=False` で自前ループ。

### メモリ断片化への防御

512KBクラスのヒープで長期稼働するための設計。**総空き容量ではなく最大連続ブロックが問題**
（TLS確立に大きな連続領域が要る）。

- `probe_largest_block()`: bytearray確保の二分探索で最大連続ブロックを実測
  （`gc.mem_free()` は断片化を見せないため）。起動時・履歴取得後・backfill送信前に記録。
- **履歴のGAS送信は半日24点ずつ** — 1日48点のペイロードはMemoryError多発（実機実測）。
- **取得直後にその場で送る**（キューに溜めない）— 溜めると取得完了直後に送信が集中する。
- **失敗は `hist_retry_queue` へ、ループ1周につき1件だけ再送** — 即時リトライは
  ヒープ状態が変わらず同じ失敗を繰り返すだけ。他の処理を挟んで断片化レイアウトが
  変わる機会を待つ。データ欠損を許容しない方針のため回数上限なし。
- **スロット書き込みとGAS送信の分離** — `send_web_cuml` はESP-NOW送信・スロット更新の後。
  GASがどれだけ失敗してもローカルデータと子機配信は無傷。
- **自己復旧（検知のみ・未武装）** — 定常運転中にweb送信が連続 `WEB_OOM_RESET`(6)回
  MemoryErrorなら断片化と判断し `web_recovery_pending` を立てる。`reset()` の呼び出しは
  実機でフラグ動作を確認するまでコメントアウト中。**根治は送信バッファのarray.array化（未着手）**。

### GAS側の受け（gas_dashboard/）

- `doPost` は `type` で分岐: `inst`（Script Propertiesへ最新値保存＋`InstLog`シートへ1行追記、
  直近1週間分のみローリング保持）/ `cuml`（`History`シートに1行追記、無期限保持）/
  `backfill`（同一時刻の行だけ差し替え）/ `boot`（再起動ログ）/ `config`（契約アンペア表示用）。
  各typeのJSONフィールド詳細は [`gas_dashboard/README.md`](../gas_dashboard/README.md) の
  「プロトコル仕様」参照。
- **backfillのペイロード形式**（2026-08-09〜）：`{created:[...], e_energy:[...]}` の配列2本
  （同じ長さ、同じ添字が対応）。旧形式 `{points:[{created,e_energy},...]}` からJSONサイズ
  約43%削減のため変更。旧形式のリクエストは受け付けない。
- **LockServiceで直列化** — GASはdoPostの同時実行を許すため、cumlとbackfillが重なると
  「読み込み→削除→再書き込み」を踏むbackfill側がデータを壊しうる。`waitLock()`は`try`の
  内側で呼び、タイムアウト時も確実に`finally`で`releaseLock()`に到達させる。
- **backfillは時刻単位で上書き** — 日付単位だと、同じ日を半日×2チャンクで送ったとき
  後のチャンクが前のチャンクを消す。
- **無音検知** — 全doPostで `lastSeenAt` を更新し、ダッシュボード表示時に最終受信からの
  経過秒数を計算、600秒（閾値`STALE_SEC`）を超えると赤画面表示。定期トリガやメール通知は
  持たない（匿名Webアプリからは`MailApp`/`ScriptApp`が権限エラーになり、承認作業を全利用者に
  強いる割に画面表示以上の価値が無いため2026-08-05に撤去）。閾値600秒は「単発再起動
  （2〜3分）では誤検知しない」値。監視のみで復旧アクションはしない。
- `d>=1` の過去日は e_energy==0 もスキップせず送る（メーター交換等の欠測をGAS側で0埋め
  として扱い、差分計算を特別扱いしないため）。`d==0` の0だけは「未計測」なので送らない。
- **デプロイの罠**: Code.js等を変更しても、GASで「新しいデプロイ」を作成しない限り
  親機が叩く `/exec` URLの動作は変わらない（テストは `/dev` URL）。また新デプロイでURLが
  変わった場合は親機の `config['WEB_GAS_URL']`（`config_main.json`、または設定用GSSの
  `WEB_GAS_URL`行）の更新が必要（コードへの直書きではない）。
- **サンプル公開デプロイ（`smm3-sample`、2026-08-10〜）**：README等に恒久リンクする公開用デプロイは、
  同一スクリプト・同一データストア（PROP/History/InstLogシート）を共有する別デプロイとして作る。
  クエリパラメータでの分岐は**使わない**（URLからパラメータを外されると実データが素通りする）。
  代わりに `Code.js` の `isSampleDeployment()` が `ScriptApp.getService().getUrl()`
  （そのデプロイ自身のURL、Google側が発行しクライアントからは偽装不能）を固定デプロイIDと
  比較して判定し、一致すれば `action=data`/`instlog`/`saveSettings` すべてで強制的に
  `SampleData.js` の固定スナップショット・テストデータ側に倒す。本番デプロイのIDとは
  一致しないため、この仕組みを追加しても本番の挙動には影響しない。

## 6. 子機（ATOM S3 / CircuitPython）の設計

- **4モード** g0〜g3 は起動時に全部組み立てて `display.root_group` の差し替えだけで切替
  （都度生成はメモリと時間を食う）。
- グラフは `displayio.Bitmap` + パレットに直接ピクセルを打つ。**警告色への変化は
  パレットの色を差し替えるだけ**（pal[1]/pal[2]を書き換え）で再描画不要、という省メモリ技法。
- 履歴は `array.array("I")`（リストの数分の1のメモリ）。`vals[0]==0` の日は
  「基準が無い＝差分が出せない」のでスキップ。
- `estimate_current_slot()`: 今日の累積値が基準値より増えている最後のスロットを現在時刻の
  代わりに使う（**子機はRTCを持たない**。時刻はデータから推定する）。
- IMU（MPU6886）を0.5秒毎に読み、重力方向で画面を自動回転。
- ボタン: 短押し=モード切替、長押し=輝度3段階循環。
- 電文パースの防御は §3 参照。CircuitPython固有の言語制約は CLAUDE.md に一覧がある。

## 7. 既知の構造的な弱点・未完了事項

改修候補を検討するときは、まずここを見る。

1. **子機のUNITが0.1固定** — 親機は D3×E1 から実UNITを計算するが、子機はハードコード。
   `M:UNT=` 配信の仕組みは書きかけのまま無効化されている。UNITが0.1以外のメーターでは
   子機の表示だけずれる。
2. **CUMLブロードキャストのロスを子機が検知できない** — ACK無しなので、30分スロットを
   取りこぼしても再取得しない（起動時のREQ以外に履歴を埋め直す手段がない）。
   欠けたスロットは翌日以降 REQ で埋まるが、当日中は欠けたまま。
3. **親機の自己復旧は未武装** — `web_recovery_pending` は検知のみ（§5）。
4. **根治策（送信経路のarray.array化）は未着手** — 現状の防御は「発生頻度を下げ、
   発生したら安全に再起動する」であり、断片化そのものは解消していない。
5. **メモリ削減実験（H1〜H1.5）の計画メモが消失** — loggerを全コメントアウト（`# H1.5:`
   プレフィックス）してあるのはこの実験の跡。実験の設計と実測値はセッション
   local_52f78207 のトランスクリプトにしか残っていない。

## 8. 変更してはいけない・変更時に必ず確認すべき箇所

- **ワイヤ電文の形式**（§3）— 親機・子機・（間接的に）GASの3者が同時に変わる。
  特に `M:ID` の後方オフセット構造と250バイト上限。
- **日跨ぎ処理の条件**（`slot_idx==1 and slot[2]!=0`）— 親機と子機で同一に保つこと。
  片方だけ変えると両者の履歴が1日ずれる。
- **302リダイレクト成功扱い**（§5）— 消すとGAS送信が全滅する。
- **WDTの生成位置**（履歴取得完了後）— 起動時に移すとブートループの危険。
- **半日24点分割・リトライキュー・スロット書き込みとGAS送信の順序**（§5）—
  どれもMemoryError実測に基づく配置。「きれいにまとめて送る」リファクタは退行になる。
- **ピクセル座標定数**（子機）— 変更時は `test_atoms3/test_watt_mock.py` で先に検証
  （CLAUDE.md「Testing Approach」）。
