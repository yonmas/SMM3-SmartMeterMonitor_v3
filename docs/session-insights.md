## 1. フリーズ問題の全体像（セッション「SMM3 フリーズ対策（実機試験中）」2026-07-04）

- **経緯**: ATOM S3子機とGASダッシュボードを追加して以来、親機のフリーズが数日に1回発生。
  それ以前は「何かあっても自動再起動で復帰、フリーズほぼゼロ」だった。
- **本命仮説**: ヒープ断片化 → CUML取得経路でMemoryError → 30分スロットが黙って欠ける。
  コード自身が `web_oom_count` と `probe_largest_block` で断片化/OOMを監視している。
- **30分境界を取りこぼす経路（可能性順）**:
  1. ESP-NOWブロードキャストのロス（子機側）— CUMLはACK無しブロードキャスト
     （smm3_main.py:425 付近）なので、子機は取りこぼしても気づけない。
  2. ヒープ断片化 → MemoryError → slot欠落（親側、本命）。
     Web I/Oでループが詰まると、発火機会をまたいで取りこぼす余地がある。
- **「再取得で直る」= バグはライブ経路側でメーターデータ側ではない**、という切り分けが成立している。
- **対策の設計方針**（採用済み・コミット履歴とも対応）:
  - スロット書き込みをGAS成否・MemoryErrorから独立させる:
    `send_web_cuml` を `send_cumul` の外（slot書き込み後）に出す／
    メーター読込前に `gc.collect()`／`web_oom_count` が高い時はWeb送信を間引く。
  - 親側: ロールオーバー時に1日1回だけ自己修復（安価・確実・無限ループ無し）。
  - ハードWDT導入＋GAS送信のtimeout退避（コミット 66da9cc）。
  - WiFi起動時自動リトライ＋WDT遅延起動＋ネット送信の犯人特定マーカー（コミット dbd85ca）。
  - GASダッシュボード側に親機データ無音検知＝状態監視（コミット ef0603c）。

## 2. GAS連携・履歴送信で踏んだバグ（セッション「SMM3 GAS」2026-06-25）

- BP35A1から1日分取得直後にその場で送信する設計（`send_web_hist_day` / `send_web_hist_half`）。
- **発見バグ3つ**:

## 3. データフロー上の非対称（セッション「SMM3」2026-06-30）

- 親機の GAS `'inst'` POSTペイロードは `{'type': 'inst', 'watt': wattage, 'muted': muted}` で
  **アンペアを含まない**。アンペア自体はBP35A1から取得済み（`amperage`変数）で、
  ESP-NOWの `M:INST` メッセージとM5Stack子機表示には使われている。
  → GAS側にアンペア表示を追加した際は2箇所の変更が必要だった（コミット b05e5d6 で対応済み）。
- 親機の例外設計: `send_web_inst` 全体が try/except で囲まれ MemoryError も捕捉
  （落ちても例外は外に飛ばない）。未捕捉例外が出ても `finally: reset()` で再起動する設計
  → 想定される故障モードは「フリーズ」より「再起動」。フリーズが起きる場合は
  この防御の外側（WDTが効かない層、I/Oブロッキング等）を疑う。

## 4. 子機（ATOM S3）側のデータモデル

- 履歴は「00:00〜24:00の30分刻みスロット」の**累積メーター値**で保持。
  各区間の使用量は隣接スロットの**差分**で算出:
  TODAYグラフ（smm3_sub_atoms3.py:387 付近）: `(hist49[n+1] - hist49[n]) * UNIT`。
- 累積値方式なので、1スロット欠けると隣接2区間の表示が壊れる
  （→ §1のスロット取りこぼし問題が表示品質に直結する理由）。
