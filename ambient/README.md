# Ambient対応版（オプション）

正式版（リポジトリ直下の `smm3_main_web.py`）は Ambient データ送信を含みません。子機(ESP-NOW)＋Web(GAS)＋Ambientの3つを同時に動かすと、メモリ制約でバックフィル（履歴データ）送信の成功率が下がることが実測で確認されたためです（詳細は下記「なぜ正式版はAmbientを含まないか」参照）。

それでも Ambient を使いたい場合向けに、このフォルダに対応版と関連情報をまとめています。

## 収録ファイル

| ファイル | 内容 |
|---|---|
| `smm3_main_web_amb.py` | **子機あり**版。子機(ESP-NOW)＋Web(GAS)＋Ambient、全部乗せ |
| `smm3_main_web_amb_mini.py` | **子機なし**版。Web(GAS)＋Ambientのみ（ESP-NOW関連コードを完全除去） |
| `smm3-lite_main_web_amb.py` | 子機あり版のliteバージョン（短期履歴メーター対応、`smm3-lite_main_web.py`ベース） |
| `smm3-lite_main_web_amb_mini.py` | 子機なし版のliteバージョン |
| `ambient_lite.py` | 軽量化した自前のAmbientクライアント（後述） |

`func_main.py` / `bp35a1.py` / `calc_charge.py` など、その他の必須ファイルはリポジトリ直下のものをそのまま使ってください（各ファイルはそれぞれのベース版にAmbient送信を追加しただけで、それ以外の依存関係はベース版と共通です）。

## どちらを使うか

| | `smm3_main_web_amb.py`（子機あり） | `smm3_main_web_amb_mini.py`（子機なし） |
|---|---|---|
| 子機（M5Stack Basic/Core2/ATOM S3）への表示 | ○ | × |
| Webダッシュボード | ○ | ○ |
| Ambient送信 | ○ | ○ |
| バックフィル送信成功率（実測） | 環境により変動（下記「なぜ正式版はAmbientを含まないか」参照） | **100%**（複数回検証、詰まりなし） |

子機の表示が要らない・親機だけで完結させたいなら、`smm3_main_web_amb_mini.py` の方が確実に動きます。子機の表示も諦めたくない場合のみ、成功率が変動するリスクを許容した上で `smm3_main_web_amb.py` を使ってください。liteバージョンが必要な場合（短期履歴メーター）は、それぞれ対応する`smm3-lite_`版を使ってください。

「バックフィル送信」とは、起動直後にスマートメーターから取得した過去30日程度の履歴データをGASへ送る処理です。ここが失敗しても自動でリトライされ続けるため（回数上限なし）、待てばいつかは埋まりますが、子機ありの構成では詰まって長時間戻らない場合が稀にあります。瞬時電力・積算電力量・Ambient自体の送信（30秒/10分間隔の定期送信）は、このバックフィルの成否とは別物で、通常通り動作します。

## なぜ正式版はAmbientを含まないか

2026-08-09、以下の検証を行いました：

- 子機(ESP-NOW)＋Web(GAS)＋Ambient を同時に動かすと、バックフィル送信の成功率が60〜78%程度に留まる（正式版のWeb単体構成はほぼ100%）
- Ambient送信を「バックフィルキューが空になるまで遅延させる」対策を試したが、**効果は誤差範囲内で確認できなかった**（同日中に交互実行した対照実験：delayed平均62.8% vs 非delayed平均63.6%）
- 子機(ESP-NOW)を外す（`smm3_main_web_amb_mini.py`）と、Ambientを維持したままバックフィル成功率が**100%**まで回復する

これらから、原因は処理タイミングの競合ではなく、**ESP-NOWがメモリを占有すること自体**が主因と判断しました。「全部乗せでフルパワーに動く」構成が実現できなかったため、正式版では子機・Web両方の信頼性を優先してAmbientを外し、Ambientを使いたい場合はこのフォルダの対応版を案内する形にしています。

**2026-08-10追記**：GAS送信先(`WEB_GAS_URL`)の扱いを見直しました。以前は設定用スプレッドシート(GSS)からの再読込みにも対応していましたが、この処理（文字列の分解・組み立てが起動シーケンス中に複数回発生する）自体がぎりぎりのメモリ状況をさらに悪化させる一因になっていたため、`smm3_main_web_amb.py`と`smm3-lite_main_web_amb.py`では**GAS送信先はconfigファイル起動時の値に固定**し、フルURL/デプロイID自動判定もやめてデプロイID限定にしました（詳しくは次章「GAS送信先の設定」参照）。あわせて、この系はもともと**同一構成でも試行間のばらつきが大きい**ことも分かっています。成功率の数字は目安程度に捉え、実際の環境で確認することをおすすめします。

## Ambientアカウントの準備

1. [ambidata.io](https://ambidata.io/) でアカウント登録し、チャンネルを作成
2. チャンネルID（`channelId`）とライトキー（`writeKey`）を控える
3. 設定用Googleスプレッドシート、または `config_main.json` の以下の項目に設定

```
A_ID   : チャンネルID
A_KEY  : ライトキー
```

`A_ID`・`A_KEY` がどちらも未設定（デフォルト値 `'*'` のまま）の場合、Ambient送信は自動的にスキップされます。

## GAS送信先（WEB_GAS_URL）の設定

このフォルダの4ファイルすべて、GAS送信先は
**`config_main.json` の `WEB_GAS_URL` に、デプロイID（`AKfycb...`で始まる文字列）だけを
記入する方式に固定**しています（正式版・`ambient/`とも共通の方針）。

```
WEB_GAS_URL : AKfycb... （デプロイIDのみ。https://... のフルURLは不可）
```

- **フルURL（`https://script.google.com/macros/s/.../exec`）は使えません**。デプロイID以外を
  入れると送信先が正しく組み立てられず、送信が失敗します
- 未設定（空文字）のままなら、Web(GAS)への送信は自動的にスキップされます

**子機あり版（`smm3_main_web_amb.py` / `smm3-lite_main_web_amb.py`）は、設定用
スプレッドシート（GSS）経由の反映は行いません**。起動時に読み込んだ`config_main.json`の
値がそのまま使われ続けます（GSS側で値を変えても反映されません）。子機なし版（mini）は
下記の通りGSS経由も使えます。

これは前述のメモリ制約への対策です（詳しくは「なぜ正式版はAmbientを含まないか」の追記参照）。
`smm3_main_web_amb_mini.py` / `smm3-lite_main_web_amb_mini.py`（子機なし版）は、
子機を使わない分メモリに余裕があるため、GSS経由の再読込みは従来通り使えます。ただし
2026-08-10以降、`WEB_GAS_URL`の値はこちらもデプロイID限定に揃えています（バリエーションを
減らすための整理で、mini版自体はフルURLでも動作する余裕がありますが、正式版・全部乗せ版と
同じくデプロイID記入で統一しています）。

## データ送信プロトコル

30秒間隔（`config['A_INTERVAL']`、デフォルト30）で、以下の内容をAmbientの `dataarray` APIへPOSTします。

```json
POST https://ambidata.io/api/v2/channels/{channelId}/dataarray
Content-Type: application/json

{
  "writeKey": "（ライトキー）",
  "data": [
    { "d1": 電流(A), "d2": 瞬時電力(W), "d3": 当月累積電力量(kWh), "d4": 当月電気料金(円) }
  ]
}
```

- 実装は `send_ambient()`（このフォルダの4ファイル共通）
- 4〜5秒未満の連投は `ambient_lite.py` 側で自動的にスキップされます（Ambient側の連投制限403相当への対策）
- **Ambientはバックフィル（過去データの後追い送信）に対応していません**。取得できた時点のデータをその場で送るのみです。取りこぼした分は後から埋められないため、GAS(Web)側の30日分の履歴に比べると、Ambient側は取得できなかった瞬間のデータが欠けることがあります

### 別のAmbient互換データベースへ差し替える場合

`ambient_lite.py` の `Ambient.__init__()` にある `self.host`（`'ambidata.io'`）と `self.path`（`/api/v2/channels/{channelId}/dataarray`）を書き換えれば、同じ `POST + JSON body` の形式を受け付ける別サーバーへ向け先を変更できます。認証方式（`writeKey`をbody に含める形）やレスポンスの扱い（`send()`はHTTPステータスを見ておらず、接続・送信が完了すれば`True`を返すのみ）が異なる場合は、`send()`内のリクエスト組み立て部分を合わせて調整してください。

## ambient_lite.py について

公式の `ambient-python-lib`（MITライセンス）をそのまま使うと、静的メモリを928バイト消費します。このリポジトリでは、`send()`（データ送信）と`__init__()`（初期化）だけを実装した最小限のクライアントに置き換えており、静的メモリ消費を304バイトまで削減しています（同一ファイルでの比較測定による実測値）。

主な違い：
- `usocket` + `settimeout()` による自前のHTTP/1.0 POST実装（`urequests`の`timeout=`引数がこのファームウェアで非対応なため）
- 公式ライブラリ側にあった「MicroPython分岐でtimeout引数を渡し忘れるバグ」を踏まない実装
- `send()`は例外を投げず、成功時`True`・失敗時`False`を返す（`.status_code`属性は持たない）

**既知の制限**：Ambient側サーバーが無応答（`EHOSTUNREACH`等）の場合、`settimeout()`で設定した秒数より長く（実測18〜19秒程度）ブロックすることがあります。原因はソケットレベルの接続確立処理がPython側のタイムアウト設定を完全には尊重していないためと推測されますが、未解明です。実害は「その回の送信が数十秒余分にかかる」程度で、無限ハングではありません。
